- 진행 방식: 세부 업무 하나의 목적·입력·처리·결과·한계를 확인하고, 사용자와 수정 사항을 정리한 뒤 다음 업무로 이동한다.

## 1. 초기 계획을 어떻게 수정했는가

초기 계획은 피처 구현 → 모델 비교 → Batch 2 평가 → 결과 정리였다. 사용자 요청으로 이 과정을 먼저 실행했으므로 남은 시간표를 재실행 중심에서 **계산·검증 설계·선택 근거·오류 해석의 공동 검토** 중심으로 바꾼다.

기존 Train 36/Validation 10 명세는 유지했고 Train 내부 3-fold CV를 추가 실행했다. CV 최저 평균 MAPE로 Ridge(alpha=0.1)와 6개 피처를 선택했다. Batch 2 오차가 크므로 계산이 맞는지와 배치·정책 일반화의 한계를 먼저 확인한다.

## 3. 한 업무를 확인하는 방식

1. 해당 업무의 목적과 전날 설계 근거를 짧게 설명한다.
2. 실제 입력·코드·표·그래프를 연결해 계산과 결과를 확인한다.
3. 확인된 사실, 아직 모르는 점, 수정 제안을 구분한다.
4. 사용자 검토 결과를 WORK_LOG에 기록하고 계획 표의 상태를 갱신한다.
5. 다음 업무로 이동한다. 현재 단계에서 결정하지 않은 추가 실험을 앞서 실행하지 않는다.

첫 업무는 **1번: 문제 정의 — 무엇을, 언제, 어떤 정보로 예측했는가**다. 이후 2번 피처 계산, 3번 분할·전처리 순서로 확인한다.

## 5. 평가와 수정 시 지킬 기준

- Batch 2는 이미 한 번 평가했다. 이번 모델·선택 기록·Test 결과를 기준 실행으로 보존한다.
- 코드 오류를 고쳐 결과를 재계산한다면 이유와 전후 결과를 기록한다. 기존 평가를 없애거나 첫 평가처럼 표현하지 않는다.
- Test 오차를 보고 피처·모델을 변경하는 후속 실험은 탐색 결과로 보고한다. 같은 Batch 2 점수를 새로운 독립 최종 평가로 주장하지 않는다.
- Train CV MAPE는 fold 밖 예측이며 최종 모델의 학습셋 재예측 점수가 아니다. Gap은 Valid−TrainCV, Test−Valid, Test−9.1이고 단위는 %p다.
- EDA에서 Batch 1 전체 라벨과 Batch 2 라벨 분포를 관측했다. 정책 중복·소표본·배치 차이를 함께 보고한다.
- 9.1%는 논문의 다른 분할 조건에서 나온 비교 기준이다. 완료 조건은 목표 달성이 아니라 재현 가능한 계산과 명확한 성능·한계 보고다.

## 6. 이미 확보한 검증과 남은 완료 조건

독립 EDA와 피처 일치, Train-only 스케일러, 저장 점수 재계산, Test 재평가 방지의 4개 검사는 통과했다. 노트북 코드 5셀을 실행하고 그림 2개를 확인했다. 이 자동 검증은 사용자와 진행하는 세부 업무 검토를 대신하지 않는다.

남은 완료 조건은 1~6번 공동 검토 기록, 필요한 수정과 후속 실험의 구분, 설명·수치가 맞는 최종 문서, 실제 PDF 페이지 확인, 제출 형식·파일 점검이다. 외부 제출은 아직 하지 않았다.

## 7. 보고서 작성 원칙

모든 주요 분석·실험은 ‘무슨 작업을 했는가 → 어떤 결과가 나왔는가 → 결과는 무엇을 의미하는가 → 다음 과정에 어떻게 활용하는가 → 왜 그 방법을 선택했는가’가 이어지도록 작성한다. 질문과 도메인 목적, 입력 데이터·계산 정의, 검증 조건을 결과와 연결한다. 수치만 나열하거나 질의응답을 그대로 붙이지 않는다.

관측 사실·원인 가설·설계 결정·미확인 사항을 구분하고, 작업 중 고민과 배운 점도 말미에 남긴다. 완료된 실험과 향후 계획을 구분한다. 이 원칙을 이후 단계의 노트북·README·결과 보고서 작성에도 적용한다.
